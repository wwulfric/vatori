# Acceptance and Smoke Tools

This document classifies the repository code that exists to verify staged framework behavior. These pieces are not product runtime APIs; they are acceptance gates, smoke harnesses or diagnostic probes used while Flow over IPC is being carved out of the compatibility runtime.

## Trace acceptance gates

- `bin/flow-ipc-trace-inspect`
- `vaadin-desktop-devtools/src/main/java/dev/vatori/desktop/devtools/DesktopTraceInspector.java`

`DesktopTraceInspector` is the strict trace gate for the smoke fixture and selected framework validation runs. Its `--require-flow-ipc-*` options are acceptance gates over recorded trace evidence, not protocol negotiation flags. Full `.ndjson` logs are generated artifacts: keep them in `.build/`, CI artifacts, release assets or external archival storage, not as one committed trace file per version. The gate list is intentionally cumulative for the main smoke path: a later gate requires earlier successful evidence unless a gate represents historical blocker evidence or a newer gate records replacement-path evidence that supersedes an older generated/lazy blocker.

The current exceptions are `--require-flow-ipc-v1_6` and the latest/delta aliases introduced at v1.37 and later. v1.6 preserves the narrowed TextField duplicate-definition blocker proof. `--require-flow-ipc-v1_7` and `--require-flow-ipc-v1_8` supersede that path and inherit from v1.5, not v1.6, because they prove the replacement stable module identity and generated/lazy resolver paths. `--require-flow-ipc-v1_37` verifies the v1.37 TextField owner reuse delta directly, `--require-flow-ipc-v1_38` verifies the v1.38 current-app owner component reuse matrix directly, `--require-flow-ipc-v1_39` verifies the v1.39 current-app owner early-import ordering delta directly, `--require-flow-ipc-v1_40` verifies the v1.40 current-app generated-imports owner side-effect delta directly, and framework-app gates from v1.46 onward verify their current slice directly; use explicit historical gates when reviewing older archived fixtures. The v1.90 LoginOverlay gate starts the focused authentication component cumulative chain, so later LoginOverlay/LoginForm cumulative gates require the auth predecessors without re-requiring the unrelated v1.57-v1.89 component/theme matrices.

## Maintenance rules

- Add new verification requirements as trace gates or smoke commands when possible.
- Keep real-window automation behind explicit `VAADIN_DESKTOP_*` environment switches.
- Keep compatibility mode and incomplete Flow over IPC boundaries visible in docs and trace names.
- Do not treat historical blocker gates as required predecessors for replacement-path gates unless the replacement still depends on that blocker evidence.
- When a gate is superseded, document the relationship here and in `DesktopTraceInspector.AcceptanceGate`.
