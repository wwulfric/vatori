# Flow Integration

## Current Integration

`vaadin-desktop-flow` integrates real Vaadin Flow through Spring Boot:

- The app uses `@SpringBootApplication`.
- Views use normal `@Route`.
- UI components are real Vaadin components.
- `DesktopLauncher` starts Spring Boot on a random local port.
- `FlowIpcLauncher` starts a minimum no-HTTP Flow IPC sidecar for constrained smoke apps.
- `SystemWebViewDesktopHost` receives the application URL and opens a macOS WKWebView desktop window by default.
- `vaadin-desktop-host-swift` can start the Java app as a sidecar and open a Swift/AppKit WKWebView through `bin/vaadin-desktop dev-swift`.
- `CompatibilityDesktopHost` remains available for headless/browser fallback modes.

This means Vaadin Flow works today with ordinary Flow development patterns.

`test-apps/flow-over-ipc-smoke-app` also uses ordinary Flow components and `@Route`, but it is launched through `FlowIpcLauncher` instead of Spring Boot web mode.

## What Is Reused

- Routing via `@Route`.
- Component tree and server-side listener model.
- Spring Boot auto-configuration from `vaadin-spring-boot-starter`.
- Vaadin Grid, Button, Span, layouts and data providers.
- Vaadin dev mode.
- In `dev-ipc`, server-side Button listener execution and basic component state mutation.

## What Still Depends on HTTP/Servlet

- Bootstrap page generation.
- Vaadin session/request lifecycle.
- Client event transport.
- UIDL/patch response transport.
- Push/WebSocket.
- Frontend resource loading, except the `dev-ipc` channel that serves `FlowBootstrap.js` and `FlowClient.js` from the Java sidecar classpath over IPC.
- Upload/download.

For the `dev-ipc` smoke app, the localhost HTTP transport is not used for bootstrap/push/event/patch/resync. The current payload now includes real server-side Vaadin UIDL generated by `UidlWriter` for bootstrap and one server-initiated push, plus `UidlRequestHandler` for click event and verification resync patches. The WebView bridge requests/imports `FlowBootstrap.js` and `FlowClient.js` over IPC, initializes the Flow bootstrap plus GWT client modules, verifies bootstrap node bindings through the registered Flow client, promotes that Flow client container to the visible WebView surface, intercepts the Flow client engine's `XMLHttpRequest` transport, forwards real click and resync UIDL RPC bodies over IPC, and delivers push UIDL to the registered Flow client. The visible Flow client consumes bootstrap, click-event, push and verification resync UIDL responses; the repository-local fallback remains for non-engine or failed-delivery diagnostics until full Flow push/reconnect/resync semantics are implemented.

These dependencies are acceptable only because they are isolated as compatibility mode.

## Code-Level Adapter Spike

`flow-transport-adapter-spike/README.md` records the first real boundary found in the local Vaadin source tree:

- `SynchronizedRequestHandler.java:58-68` already supports pre-reading body and post-lock response writing.
- `UidlRequestHandler.java:122-173` is the event-to-UIDL path.
- `UidlRequestHandler.java:191-202` delegates UIDL writing to `UidlWriter`.
- `UidlWriter.java:120-195` can produce patch JSON from `UI`.
- `ServerRpcHandler.java:343-353` and `VaadinService.java:1410-1424` still require `VaadinRequest` for deployment config and UI lookup.

Conclusion: patch generation is not the hardest boundary. Request-derived session/UI/security context is the first hard dependency to isolate.

## Target Flow over IPC Work

Next work should replace the compatibility adapter with a real Flow transport adapter:

1. Locate Flow client event handler entry points.
2. Locate server-side patch/UIDL output points.
3. Wrap them behind a `FlowTransport` SPI.
4. Feed transport messages through `vaadin-desktop-ipc`.
5. Execute Flow client engine resources loaded through IPC or a local asset protocol in the native host.

The current concrete issue is to keep tightening this repository-local adapter: it accepts `(VaadinSession, UI, requestBody, metadata)` and returns UIDL JSON while using a compatibility `VaadinRequest` only at the edge. The WebView bridge now provides Flow-client-shaped click and verification resync RPC request bodies directly, bootstrap mirrors Flow's `Vaadin-Security-Key`, event/resync envelopes carry that key back to Java, the runtime rejects mismatched Flow IPC `sessionId`/`uiId`, `csrfToken`/security key, stale `syncId` and out-of-order `clientId` values before dispatch, Java-to-WebView payloads expose monotonic `serverSequence` diagnostics, and `FlowBootstrap.js` / `FlowClient.js` are available over IPC as classpath resources and initialized inside WKWebView as the visible renderer. The remaining work is broader Flow-client event coverage plus real push queue, reconnect and full resync semantics.

That issue has now started in compiled framework code:

- `dev.vatori.desktop.flow.transport.UidlFlowTransportAdapter`
- `dev.vatori.desktop.flow.transport.DesktopVaadinRequest`
- `dev.vatori.desktop.flow.transport.DesktopVaadinResponse`
- `dev.vatori.desktop.flow.transport.DesktopWrappedSession`
- `dev.vatori.desktop.flow.transport.DesktopFlowRuntimeSession`
- `dev.vatori.desktop.flow.transport.UidlAdapterSmokeMain`
- `dev.vatori.desktop.flow.transport.UidlRpcSmokeMain`
- `dev.vatori.desktop.flow.ipc.FlowClientResources`
- `dev.vatori.desktop.flow.ipc.FlowClientResourceSmokeMain`

This adapter now has a runnable smoke command:

```bash
bash bin/uidl-adapter-smoke
bash bin/uidl-rpc-smoke
bash bin/flow-client-resource-smoke
```

The smoke constructs an in-process desktop-shaped `VaadinSession`/`UI` and verifies that real `UidlWriter` output includes UIDL `changes`, `syncId` and the bootstrap `Vaadin-Security-Key`. `dev-ipc` now reuses that session shape to include real UIDL in bootstrap and patch payloads without a servlet container for that narrow path.

The RPC smoke verifies the next boundary: `UidlRequestHandler` can find the desktop `UI`, run `ServerRpcHandler` for a real `type=event` click RPC and return listener-produced UIDL without a real HTTP socket. The resource smoke verifies that the Java sidecar can read Vaadin `flow-client` resources from its classpath and expose augmented `FlowBootstrap.js` / `FlowClient.js` for IPC delivery. `dev-ipc` now uses the same server-side path with WebView-provided click and resync UIDL RPC bodies.

The exact remaining runtime inputs are still: broader WebView-side Flow-client event coverage, full resync semantics, real push queue/reconnect behavior and full frontend resource coverage.
