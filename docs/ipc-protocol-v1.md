# Flow IPC Protocol v1

Flow IPC Protocol v1 is the first runtime protocol for moving Vaadin Desktop beyond localhost HTTP compatibility mode.

Current implementation status: **minimum runtime slice implemented with UIDL writer, visible Flow client engine ownership for bootstrap, click-event patches, two ordered server pushes, duplicate/late probe recovery resync, IPC-backed Flow client XHR dispatch, and real Flow client resource loading/init**. It supports a local WebView shell, Java sidecar stdin/stdout transport, bootstrap, event, replace-root patch, desktop command/capabilityResult, push, resync, resource request/response and shutdown. The runtime generates bootstrap and push UIDL with `UidlWriter`; bootstrap UIDL carries Flow's `Vaadin-Security-Key`; the WebView imports `FlowBootstrap.js` and an augmented `FlowClient.js`, promotes the registered Flow client container to the visible surface, installs an `XMLHttpRequest` shim for the Flow client engine and sends the real Flow client click/resync UIDL RPC over IPC with CSRF/security key, `syncId`, `clientId` and Flow node id. Java dispatches those bodies through `UidlRequestHandler`/`ServerRpcHandler` to produce UIDL patches consumed by the visible Flow client. The frontend resource channel now also executes one ordinary Flow `LoadMode.LAZY` dependency through the visible DependencyLoader, records production owner boundaries through v1.20, records a v1.21 unified frontend resolver contract across flow-client, component frontend, theme/static, generated/lazy, Flow lazy dependency, production owner and dev-mode families, verifies a v1.22 generated chunk-file positive fixture, verifies a v1.23 production owner positive runtime fixture, records v1.24-v1.25 closure/product-path baseline contracts and records v1.26-v1.31 generated lazy source/build/app-output/build-step availability blocker evidence. The repository-local UIDL applier remains as a diagnostic fallback for non-engine or failed-delivery paths.

## Prefixes

Swift host trace:

```text
HOST_PROTOCOL {"direction":"recv","type":"launch",...}
```

Flow IPC envelopes between WebView/host and Java sidecar:

```text
VFIPC1 {"version":"flow-ipc-v1","type":"bootstrapRequest",...}
```

Compatibility-mode desktop capability command envelopes from Java to host:

```text
VDP1 {"type":"command","id":"desktop-command-1",...}
```

In `dev-ipc`, desktop capability commands also use `VFIPC1` Flow IPC envelopes:

```text
VFIPC1 {"version":"flow-ipc-v1","type":"command","id":"desktop-command-1",...}
```

## Envelope

```json
{
  "version": "flow-ipc-v1",
  "type": "event",
  "id": "webview-3",
  "correlationId": "webview-3",
  "sessionId": "flow-ipc-session",
  "uiId": "main",
  "route": "",
  "payload": {
    "dispatch": "flow-client-xhr",
    "componentId": "ipc-button",
    "nodeId": 16,
    "securityKey": "trace-csrf",
    "event": "uidl-rpc",
    "uidlRpc": {
      "csrfToken": "trace-csrf",
      "rpc": [
        {
          "type": "event",
          "node": 16,
          "event": "click",
          "data": {}
        }
      ],
      "syncId": -1,
      "clientId": 1
    }
  },
  "error": null,
  "timestamp": 1778997000000
}
```

Fields:

- `version`: protocol version, currently `flow-ipc-v1`.
- `type`: message type.
- `id`: message id.
- `correlationId`: request/response correlation id.
- `sessionId`: desktop Flow session id.
- `uiId`: desktop UI/window id.
- `route`: Flow route.
- `payload`: message payload.
- `error`: structured error or `null`.
- `timestamp`: sender timestamp in epoch milliseconds.

## Current Patch Payload

The current patch payload has two parts:

- `uidl`: real Vaadin server-side UIDL generated by `UidlWriter` for bootstrap or `UidlRequestHandler` for event patches.
- `tree`: repository-local render tree retained as a diagnostic fallback while the visible Flow client engine consumes bootstrap, click-event, push and recovery resync UIDL.

```json
{
  "patchType": "replaceRoot",
  "reason": "event",
  "transport": "flow-ipc",
  "compatibilityMode": false,
  "uidl": {
    "source": "UidlRequestHandler",
    "format": "vaadin-uidl-json",
    "containsChanges": true,
    "containsSyncId": true,
    "consumedByWebView": true,
    "consumer": "flow-client-engine-visible",
    "body": "{\"clientId\":0,\"changes\":[{\"node\":13,\"type\":\"put\",\"key\":\"text\",\"feat\":7,\"value\":\"Clicks: 1\"}],\"syncId\":-1}"
  },
  "tree": {
    "id": "ipc-root",
    "tag": "vaadin-vertical-layout",
    "kind": "layout",
    "text": "",
    "clickable": false,
    "children": []
  }
}
```

The UIDL is real server-side Flow output. Bootstrap, click-event patches, two ordered server pushes and one recovery resync are consumed by the visible Flow client engine after the WebView imports `FlowBootstrap.js` / `FlowClient.js` and promotes the registered client container to `#flow-client-engine-root`. The local render tree remains for diagnostics and failed-delivery fallback.

## Current Bootstrap Security Key

Vaadin Flow's browser bootstrap normally adds `ApplicationConstants.UIDL_SECURITY_TOKEN_ID`, serialized as `Vaadin-Security-Key`, after `UidlWriter.createUidl(...)`. The IPC runtime now mirrors that bootstrap step in `DesktopFlowRuntimeSession.createBootstrapUidl()`.

The WebView bridge reads the key from `clientState.securityKey` and from the bootstrap UIDL body, then sends it back on event and resync envelopes. The UIDL RPC body still uses Flow's regular `csrfToken` field because that is what `ServerRpcHandler` validates. In the current bridge, `securityKey` and `csrfToken` are the same UI token.

## Current Push Payload

`dev-ipc` v1.1 emits two server-initiated `push` updates after bootstrap. The Java runtime mutates the server-side Flow component tree and serializes each async delta with `UidlWriter`. Because early pushes can arrive before `FlowClient.js` is imported and registered, the WebView bridge queues them, records queue/flush order with the Java `serverSequence`, then delivers the UIDL body into the visible Flow client engine through the IPC message bridge.

```json
{
  "type": "push",
  "payload": {
    "reason": "server-initiated-update",
    "pushIndex": 2,
    "ordering": {
      "mode": "monotonic-server-sequence",
      "expectedAction": "deliver-in-order"
    },
    "transport": "flow-ipc",
    "compatibilityMode": false,
    "uidlWriter": true,
    "uidl": {
      "source": "UidlWriter",
      "reason": "push",
      "async": true,
      "consumedByWebView": true,
      "consumer": "flow-client-engine-visible"
    }
  }
}
```

The outer `serverSequence` remains monotonic for every Java-to-WebView envelope. The v1.1 smoke also emits one controlled duplicate/late probe:

```json
{
  "type": "push",
  "payload": {
    "reason": "server-initiated-duplicate-late-probe",
    "pushIndex": 2,
    "orderingProbe": {
      "kind": "duplicate-late",
      "effectiveServerSequence": 4,
      "expectedAction": "ignore-and-request-resync"
    }
  }
}
```

The WebView ordering layer treats `orderingProbe.effectiveServerSequence` as the message sequence to evaluate. The duplicate/late probe is not delivered to the Flow client engine a second time; it is recorded under ignored-order diagnostics and triggers `reason=ordering-recovery-duplicate-late` resync. This is a controlled smoke recovery model, not durable reconnect or full Flow Push/WebSocket parity.

## Current Event Payload

`dev-ipc` no longer sends only `{action, componentId}`. The verified path calls the real Flow client engine. Its XHR request is intercepted by the Swift WebView bridge and forwarded as a Flow-client-shaped UIDL RPC object:

```json
{
  "type": "event",
  "payload": {
    "dispatch": "flow-client-xhr",
    "componentId": "ipc-button",
    "nodeId": 16,
    "securityKey": "trace-csrf",
    "event": "uidl-rpc",
    "uidlRpc": {
      "csrfToken": "trace-csrf",
      "rpc": [
        {
          "type": "event",
          "node": 16,
          "event": "click",
          "data": {}
        }
      ],
      "syncId": -1,
      "clientId": 1
    }
  }
}
```

The Java side still retains a legacy translator for the old simplified event payload as a fallback, but the verified path is `dispatch=flow-client-xhr`. The first Flow client XHR message may be `attachExistingElementById` with `clientId=0`; the desktop runtime acknowledges it and advances Vaadin's internal client-to-server message id before the actual click RPC arrives with `clientId=1`.

The v1.1 smoke path also forwards non-button Flow client events through the same envelope shape. Native `Input` and checkbox `change` events preserve Flow event data under `uidlRpc.rpc[].data`, for example `{"element.value":"Flow IPC typed"}` for `ipc-text-input` and `{"element.checked":true}` for `ipc-checkbox`. Java handles both through `UidlRequestHandler` and returns visible Flow client patches for `Text input: Flow IPC typed` and `Checkbox: checked`.

The Java runtime checks the outer envelope `sessionId` and `uiId` before event dispatch. A mismatch is rejected as `invalidClientState` before the UIDL RPC body reaches `UidlRequestHandler`.

## Error Model

Errors use the same envelope with `type=error` and an `error` object:

```json
{
  "type": "error",
  "id": "webview-5",
  "sessionId": "flow-ipc-session",
  "uiId": "main",
  "payload": {
    "reason": "verification-error-probe"
  },
  "error": {
    "code": "webviewVerificationProbe",
    "message": "Verification error probe from WebView bridge"
  }
}
```

`invalidCsrfToken` is emitted when a WebView `event` envelope carries a security key or UIDL RPC body whose `csrfToken` does not match the desktop `UI` token. `invalidClientState` is emitted for malformed or stale envelope/UIDL RPC metadata such as mismatched `sessionId`/`uiId`, missing/mismatched `syncId` or out-of-order `clientId`. The runtime rejects those messages before they reach `UidlRequestHandler`. The WebView bridge can also originate `type=error` envelopes; the verification hook uses `webviewVerificationProbe` so the trace contains a client-side error-reporting example without breaking the normal app path.
