# Flow IPC Protocol v1

Flow IPC Protocol v1 is the first runtime protocol for moving Vaadin Desktop beyond localhost HTTP compatibility mode.

Current implementation status: **minimum runtime slice implemented with UIDL writer, visible Flow client engine ownership for bootstrap, click-event patches, two ordered server pushes, duplicate/late probe recovery resync, IPC-backed Flow client XHR dispatch, and real Flow client resource loading/init**. It supports a local WebView shell, Java sidecar stdin/stdout transport, bootstrap, event, replace-root patch, desktop command/capabilityResult, push, resync, resource request/response and shutdown. The runtime generates bootstrap and push UIDL with `UidlWriter`; bootstrap UIDL carries Flow's `Vaadin-Security-Key`; the WebView imports `FlowBootstrap.js` and an augmented `FlowClient.js`, promotes the registered Flow client container to the visible surface, installs an `XMLHttpRequest` shim for the Flow client engine and sends the real Flow client click/resync UIDL RPC over IPC with CSRF/security key, `syncId`, `clientId` and Flow node id. Java dispatches those bodies through `UidlRequestHandler`/`ServerRpcHandler` to produce UIDL patches consumed by the visible Flow client. The repository-local UIDL applier remains as a diagnostic fallback for non-engine or failed-delivery paths.

## Prefixes

Swift host trace:

```text
HOST_PROTOCOL {"direction":"recv","type":"launch",...}
```

Flow IPC envelopes between WebView/host and Java sidecar:

```text
VFIPC1 {"version":"flow-ipc-v1","type":"bootstrapRequest",...}
```

Compatibility-mode desktop capability command envelopes from Java to host:

```text
VDP1 {"type":"command","id":"desktop-command-1",...}
```

In `dev-ipc`, desktop capability commands also use `VFIPC1` Flow IPC envelopes:

```text
VFIPC1 {"version":"flow-ipc-v1","type":"command","id":"desktop-command-1",...}
```

## Envelope

```json
{
  "version": "flow-ipc-v1",
  "type": "event",
  "id": "webview-3",
  "correlationId": "webview-3",
  "sessionId": "flow-ipc-session",
  "uiId": "main",
  "route": "",
  "payload": {
    "dispatch": "flow-client-xhr",
    "componentId": "ipc-button",
    "nodeId": 16,
    "securityKey": "trace-csrf",
    "event": "uidl-rpc",
    "uidlRpc": {
      "csrfToken": "trace-csrf",
      "rpc": [
        {
          "type": "event",
          "node": 16,
          "event": "click",
          "data": {}
        }
      ],
      "syncId": -1,
      "clientId": 1
    }
  },
  "error": null,
  "timestamp": 1778997000000
}
```

Fields:

- `version`: protocol version, currently `flow-ipc-v1`.
- `type`: message type.
- `id`: message id.
- `correlationId`: request/response correlation id.
- `sessionId`: desktop Flow session id.
- `uiId`: desktop UI/window id.
- `route`: Flow route.
- `payload`: message payload.
- `error`: structured error or `null`.
- `timestamp`: sender timestamp in epoch milliseconds.

## Current Patch Payload

The current patch payload has two parts:

- `uidl`: real Vaadin server-side UIDL generated by `UidlWriter` for bootstrap or `UidlRequestHandler` for event patches.
- `tree`: repository-local render tree retained as a diagnostic fallback while the visible Flow client engine consumes bootstrap, click-event, push and recovery resync UIDL.

```json
{
  "patchType": "replaceRoot",
  "reason": "event",
  "transport": "flow-ipc",
  "compatibilityMode": false,
  "uidl": {
    "source": "UidlRequestHandler",
    "format": "vaadin-uidl-json",
    "containsChanges": true,
    "containsSyncId": true,
    "consumedByWebView": true,
    "consumer": "flow-client-engine-visible",
    "body": "{\"clientId\":0,\"changes\":[{\"node\":13,\"type\":\"put\",\"key\":\"text\",\"feat\":7,\"value\":\"Clicks: 1\"}],\"syncId\":-1}"
  },
  "tree": {
    "id": "ipc-root",
    "tag": "vaadin-vertical-layout",
    "kind": "layout",
    "text": "",
    "clickable": false,
    "children": []
  }
}
```

The UIDL is real server-side Flow output. Bootstrap, click-event patches, two ordered server pushes and one recovery resync are consumed by the visible Flow client engine after the WebView imports `FlowBootstrap.js` / `FlowClient.js` and promotes the registered client container to `#flow-client-engine-root`. The local render tree remains for diagnostics and failed-delivery fallback.

## Current Bootstrap Security Key

Vaadin Flow's browser bootstrap normally adds `ApplicationConstants.UIDL_SECURITY_TOKEN_ID`, serialized as `Vaadin-Security-Key`, after `UidlWriter.createUidl(...)`. The IPC runtime now mirrors that bootstrap step in `DesktopFlowRuntimeSession.createBootstrapUidl()`.

The WebView bridge reads the key from `clientState.securityKey` and from the bootstrap UIDL body, then sends it back on event and resync envelopes. The UIDL RPC body still uses Flow's regular `csrfToken` field because that is what `ServerRpcHandler` validates. In the current bridge, `securityKey` and `csrfToken` are the same UI token.

## Current Push Payload

`dev-ipc` v1.1 emits two server-initiated `push` updates after bootstrap. The Java runtime mutates the server-side Flow component tree and serializes each async delta with `UidlWriter`. Because early pushes can arrive before `FlowClient.js` is imported and registered, the WebView bridge queues them, records queue/flush order with the Java `serverSequence`, then delivers the UIDL body into the visible Flow client engine through the IPC message bridge.

```json
{
  "type": "push",
  "payload": {
    "reason": "server-initiated-update",
    "pushIndex": 2,
    "ordering": {
      "mode": "monotonic-server-sequence",
      "expectedAction": "deliver-in-order"
    },
    "transport": "flow-ipc",
    "compatibilityMode": false,
    "uidlWriter": true,
    "uidl": {
      "source": "UidlWriter",
      "reason": "push",
      "async": true,
      "consumedByWebView": true,
      "consumer": "flow-client-engine-visible"
    }
  }
}
```

The outer `serverSequence` remains monotonic for every Java-to-WebView envelope. The v1.1 smoke also emits one controlled duplicate/late probe:

```json
{
  "type": "push",
  "payload": {
    "reason": "server-initiated-duplicate-late-probe",
    "pushIndex": 2,
    "orderingProbe": {
      "kind": "duplicate-late",
      "effectiveServerSequence": 4,
      "expectedAction": "ignore-and-request-resync"
    }
  }
}
```

The WebView ordering layer treats `orderingProbe.effectiveServerSequence` as the message sequence to evaluate. The duplicate/late probe is not delivered to the Flow client engine a second time; it is recorded under ignored-order diagnostics and triggers `reason=ordering-recovery-duplicate-late` resync. This is a controlled smoke recovery model, not durable reconnect or full Flow Push/WebSocket parity.

## Current Event Payload

`dev-ipc` no longer sends only `{action, componentId}`. The verified path calls the real Flow client engine. Its XHR request is intercepted by the Swift WebView bridge and forwarded as a Flow-client-shaped UIDL RPC object:

```json
{
  "type": "event",
  "payload": {
    "dispatch": "flow-client-xhr",
    "componentId": "ipc-button",
    "nodeId": 16,
    "securityKey": "trace-csrf",
    "event": "uidl-rpc",
    "uidlRpc": {
      "csrfToken": "trace-csrf",
      "rpc": [
        {
          "type": "event",
          "node": 16,
          "event": "click",
          "data": {}
        }
      ],
      "syncId": -1,
      "clientId": 1
    }
  }
}
```

The Java side still retains a legacy translator for the old simplified event payload as a fallback, but the verified path is `dispatch=flow-client-xhr`. The first Flow client XHR message may be `attachExistingElementById` with `clientId=0`; the desktop runtime acknowledges it and advances Vaadin's internal client-to-server message id before the actual click RPC arrives with `clientId=1`.

The v1.1 smoke path also forwards non-button Flow client events through the same envelope shape. Native `Input` and checkbox `change` events preserve Flow event data under `uidlRpc.rpc[].data`, for example `{"element.value":"Flow IPC typed"}` for `ipc-text-input` and `{"element.checked":true}` for `ipc-checkbox`. Java handles both through `UidlRequestHandler` and returns visible Flow client patches for `Text input: Flow IPC typed` and `Checkbox: checked`.

The Java runtime checks the outer envelope `sessionId` and `uiId` before event dispatch. A mismatch is rejected as `invalidClientState` before the UIDL RPC body reaches `UidlRequestHandler`.

## Current Resync Payload

When `VAADIN_DESKTOP_FLOW_IPC_AUTO_RESYNC=1` is set for verification, the WebView bridge requests one resync after the duplicate/late push probe is ignored and the component-event matrix has completed. The Swift bridge forwards that Flow-client-shaped body as a `resync` envelope. Java responds with a normal `patch` envelope whose UIDL payload is generated through `UidlRequestHandler` with `resync=true`, and the Swift bridge completes the pending Flow client XHR with that UIDL response.

```json
{
  "type": "resync",
  "payload": {
    "dispatch": "flow-client-xhr",
    "reason": "ordering-recovery-duplicate-late",
    "securityKey": "trace-csrf",
    "event": "uidl-resync",
    "uidlRpc": {
      "csrfToken": "trace-csrf",
      "resynchronize": true,
      "rpc": [],
      "syncId": -1,
      "clientId": 5,
      "reason": "ordering-recovery-duplicate-late"
    },
    "syncId": -1,
    "clientId": 5
  }
}
```

## Current Command Payload

Desktop API calls in `dev-ipc` use the same envelope with `type=command`:

```json
{
  "type": "command",
  "id": "desktop-command-3",
  "correlationId": "desktop-command-3",
  "payload": {
    "command": "clipboard.writeText",
    "args": {
      "text": "Vaadin Flow over IPC clicks: 1"
    }
  }
}
```

The Swift host responds with `type=capabilityResult`:

```json
{
  "type": "capabilityResult",
  "id": "capability-desktop-command-3",
  "correlationId": "desktop-command-3",
  "payload": {
    "success": true,
    "command": "clipboard.writeText",
    "mode": "native-nspasteboard",
    "permissionMode": "manifest-enforced",
    "permissionDecision": "allowed",
    "permissionReason": "manifest-allow",
    "permissionScope": "window:main"
  }
}
```

Implemented host commands in `dev-ipc`:

- `window.setTitle`: updates the AppKit `NSWindow` title.
- `clipboard.writeText`: writes to macOS `NSPasteboard`.
- `fileDialog.openFile`: opens AppKit `NSOpenPanel` and returns `mode=native-appkit-open-panel` with `canceled`, `paths`, `allowsMultipleSelection`, `securityScoped=false` and `autoCanceled` metadata. The v1 sample fixture still contains the older `mode=scaffold-cancelled` cancellation result and remains accepted by the inspector for backward compatibility.
- `fileTransfer.download`: bounded v1.1 smoke command that writes a small UTF-8 body to a controlled path or a user-selected `NSSavePanel` path. Trace output redacts the body and records `operation=download`, `mode`, `byteCount`, `declaredByteCount`, `filename`, `path`, `bodyRedacted=true` and permission metadata.
- `fileTransfer.selectUploadFile`: bounded v1.1 smoke command that uses a controlled selected file path or `NSOpenPanel`, reads metadata and a capped sample, and returns `operation=upload`, `mode`, `byteCount`, `sampledBytes`, `filename`, `path`, `securityScoped=false`, `bodyRedacted=true` and permission metadata.
- `notification.show`: accepted as trace-only scaffold.

The v1.1 capability permission model is still deliberately small, but it is no longer hard-coded to one mode. `desktop-capabilities.json` can select `permissionMode=allow-all-dev`, `permissionMode=manifest-enforced` or `permissionMode=trace-only-dry-run`. The Flow IPC smoke app uses `manifest-enforced`: declared commands for the `main` window return `permissionDecision=allowed` with `permissionReason=manifest-allow`, while its intentionally undeclared `diagnostics.deniedCapability` smoke command returns `permissionDecision=denied` with `permissionReason=manifest-denied`. Unsupported commands that are explicitly listed in a manifest are still rejected as `unsupported-command`. The next production model should replace these development modes with a manifest-gated policy keyed by window, origin, user gesture and capability.

## Error Model

Errors use the same envelope with `type=error` and an `error` object:

```json
{
  "type": "error",
  "id": "webview-5",
  "sessionId": "flow-ipc-session",
  "uiId": "main",
  "payload": {
    "reason": "verification-error-probe"
  },
  "error": {
    "code": "webviewVerificationProbe",
    "message": "Verification error probe from WebView bridge"
  }
}
```

`invalidCsrfToken` is emitted when a WebView `event` envelope carries a security key or UIDL RPC body whose `csrfToken` does not match the desktop `UI` token. `invalidClientState` is emitted for malformed or stale envelope/UIDL RPC metadata such as mismatched `sessionId`/`uiId`, missing/mismatched `syncId` or out-of-order `clientId`. The runtime rejects those messages before they reach `UidlRequestHandler`. The WebView bridge can also originate `type=error` envelopes; the verification hook uses `webviewVerificationProbe` so the trace contains a client-side error-reporting example without breaking the normal app path.

## Compatibility Strategy

- `dev` and `dev-swift` remain compatibility HTTP modes.
- `dev-ipc` uses Flow IPC Protocol v1 and must log `transport=flow-ipc` and `compatibilityMode=false`.
- Full push queue/reconnect semantics and full push/WebSocket replacement remain future work. The current resource loading slice serves and verifies the advertised Flow client classpath resource graph over IPC, imports and initializes `FlowBootstrap.js` / augmented `FlowClient.js`, verifies bootstrap UIDL binding, classifies executed vs verified-only resources, performs one `flow-client-lazy-lookup` probe for `Flow.js`, and makes the registered GWT client the visible UIDL renderer for bootstrap, click-event, ordered push and recovery resync patches. The v1.2 component resource slice adds `componentFrontendResources` to bootstrap, requests the real `META-INF/resources/frontend/vaadin-big-decimal-field.js` classpath module, declares BigDecimalField import rewrites in the manifest, dynamically imports the real module in the no-localhost WebView, and traces `blockedReason` / `failureClassification` for the remaining npm frontend gap. The v1.4 slice also covers focused TextField/Checkbox/Select dev-bundle entries, one real theme/static classpath CSS resource, one verified repository-local generated Flow imports fixture resource, one verified real Vaadin dev-bundle `generated-flow-imports-*.js` chunk plus markdown helper dependency, one verified Vaadin dev-bundle `config/stats.json` production graph resource and one verified Vaadin dev-bundle `package-lock.json` package graph resource while keeping production bundle execution partial and dev-mode/Vite execution plus Flow-client-engine-triggered generated lazy execution as blockers. The v1.5 slice adds Blob-backed no-localhost staging evidence for executed artifacts and strict blockers, including TextField staged blocker evidence and generated/lazy staged execution attempt evidence. The v1.6 slice narrows the TextField blocker to production `indexhtml` reimport side effects and duplicate `vaadin-text-field` custom element registration; the v1.7 slice resolves that layer with stable module identity and verifies a real Flow `TextField` event path; the v1.8 slice resolves generated/lazy relative dependency staging and executes the real generated-flow-imports chunk plus markdown helper while keeping Flow-client-engine-triggered `loadOnDemand` as the next boundary. The v1.1 push ordering slice verifies two ordered server pushes, one duplicate/late probe, ignored-order diagnostics and explicit recovery resync, but not durable reconnect after host reload or process crash. Upload/download now has a minimal controlled-path smoke boundary, but full Vaadin Upload/Download parity, binary streaming, progress and sandbox-safe file grants remain future work.
