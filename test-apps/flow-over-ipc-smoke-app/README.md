# Flow over IPC Smoke App

This is the first independent developer-shaped app for the `dev-ipc` runtime path.

Run:

```bash
bash bin/vaadin-desktop dev-ipc test-apps/flow-over-ipc-smoke-app
```

Expected transport:

- `transport=flow-ipc`
- `compatibilityMode=false`
- no `Application URL: http://127.0.0.1:...` is required for the core UI path

Current scope:

- Real Vaadin Flow Java components are instantiated in the Java sidecar.
- The Swift/AppKit host loads a local WebView shell instead of a localhost URL.
- The full advertised Flow client classpath resource graph is requested over IPC. `FlowBootstrap.js` / `FlowClient.js` are imported, the remaining resources are classified as verified-only / intentionally-not-executed, a dynamic `flow-client-lazy-lookup` probe verifies `Flow.js`, and the Flow client container becomes the visible WebView renderer for bootstrap, click-event patches, ordered push and recovery resync.
- The smoke view's `ipc-list` contains four Flow `Span` rows; `webview.dom` diagnostics verify that the visible Flow client bound and rendered all four list items.
- Button events travel visible Flow client -> IPC-backed XHR shim -> Swift host -> Java stdin as `VFIPC1` envelopes carrying Flow UIDL RPC payloads.
- The v1.1 component matrix adds a native Flow `Input` text field and checkbox. Their `change` events travel through the same visible Flow client -> IPC-backed XHR -> Java listener -> UIDL patch path, carrying `element.value` and `element.checked` event data.
- The v1.2 matrix adds `com.vaadin.flow.component.textfield.BigDecimalField`, a real Vaadin Web Component. Bootstrap advertises `META-INF/resources/frontend/vaadin-big-decimal-field.js`; the WebView requests it over IPC, imports the real classpath module with v1.4 manifest rewrites, resolves `lit` through a focused extracted Lit CSS helper, keeps `@vaadin/text-field` as the remaining controlled shim, resolves `@vaadin/component-base/src/define.js` through an extracted Vaadin dev-bundle define helper, verifies the focused TextField production class entry as a partial blocker resource with a recorded `outlet._root` replacement blocker, dispatches a DOM `change` event from `vaadin-big-decimal-field`, and verifies `Vaadin BigDecimalField: 42.5` through the Java listener -> `UidlRequestHandler` -> visible Flow client DOM path.
- The v1.4 frontend artifact manifest also advertises one theme/static classpath CSS resource. The WebView requests it over IPC, verifies the sha256/body metadata, injects it into the local shell and records `flowClientResourceThemeLookupResult=verified:...`.
- The generated/lazy slice verifies both the repository-local generated Flow imports fixture and the real Vaadin dev-bundle `generated-flow-imports-*.js` chunk plus its markdown helper dependency over the same IPC resource channel. v1.8 executes the real dev-bundle chunk and helper through staged relative-import resolution; v1.9 records the real `Flow.loadOnDemand` API owner/install source, requested chunk, registry/mapping source and `flow-ipc-loadondemand-v1_9` blocker. v1.10 adds a separate real Flow `LoadMode.LAZY` dependency declared with `@JavaScript`; the visible Flow DependencyLoader requests it, the host resolves it through IPC and executes it as a staged module. v1.11 captures a real UIDL generated `Flow.loadOnDemand(chunkId)` request from the visible Flow client, maps it to the generated-flow-imports artifact, stages/imports it, and records the remaining chunk-file gap as `flow-ipc-loadondemand-chunk-v1_11`. v1.12 parses the real generated-flow-imports body and records that the current Vaadin build's loadOnDemand table is a no-op, with `chunkFileStatus=not-generated` and `loadOnDemandChunkFileFailureLayer=chunk-file-not-generated`. v1.17 moves the ordinary Flow lazy dependency execution path from Blob-only staging to a Swift-owned `vatori-resource://` file-backed custom-scheme URL and records handler request/response plus execution evidence.
- The production-bundle slice now verifies the Vaadin dev-bundle stats graph, stages the selected production `indexhtml` artifact as a v1.10 execution attempt, adds a v1.13 runtime owner contract for that artifact, adds a v1.14 controlled owner import attempt, adds a v1.15 owner dependency resolver closure, adds a v1.16 owner import ordering / component reuse boundary, adds a v1.18 production owner custom-scheme resource graph boundary, adds a v1.19 production owner side-effect / component reuse decision boundary and adds a v1.20 owner-owned runtime reuse attempt boundary. The owner evidence is explicit (`owner=production-bundle-runtime`, owner module identity, cache/cleanup policy and `componentProductionOwnerReused=false`); v1.14 records import preflight, dependency rewrite diagnostics, Vaadin global snapshots, registry snapshots, browser error metadata and the `production-owner-relative-import-unresolved` blocker. v1.15 then resolves/stages existing real owner relative dependencies, records phase candidates for isolated/pre-component diagnostics, classifies missing real artifacts by path/specifier and narrows the current blocker to `production-owner-missing-real-artifact`. v1.16 records `before-component-imports` owner-first preflight, after-component fallback, observed phases, component reuse decisions and the current duplicate custom element / component reuse contract blocker. v1.18 stages the stats-selected owner root and resolved dependencies as `vatori-resource://flow-ipc/production-owner/...`, records root/dependency handler request/response and disables root Blob fallback as a passing condition. v1.19 records owner module import vs side-effect satisfaction and the current `focused-fallback-after-owner-side-effect-check` component decision. v1.20 moves the owner-first attempt before focused component imports and currently records `production-owner-owned-missing-real-artifact` with `focused-fallback-after-owner-owned-runtime-attempt`. This is ordering/reuse/resource-loader/side-effect decision evidence, not production owner import success.
- Java emits two server-initiated push UIDL updates after bootstrap; the WebView bridge queues early pushes until the visible Flow client engine is ready, then flushes and consumes them without localhost HTTP.
- Java also emits one controlled duplicate/late push probe. The WebView ignores it deterministically, records delivered/ignored order diagnostics and triggers an explicit `ordering-recovery-duplicate-late` resync.
- Java-to-WebView payloads include monotonic `serverSequence` diagnostics for the smoke path.
- Java listener execution updates Flow component state and returns a full replace-root patch.
- With `VAADIN_DESKTOP_FLOW_IPC_AUTO_RESYNC=1`, the verification hook completes the ordering-recovery resync path after the duplicate/late probe and component-event matrix, falling back to an IPC-backed Flow XHR body if the current engine method does not emit XHR, and consumes the returned `UidlRequestHandler` response.
- Desktop API calls travel Java -> Swift host as `VFIPC1 command`.
- `desktop-capabilities.json` declares `permissionMode=manifest-enforced` and allows `window.setTitle`, `notification.show`, `clipboard.writeText`, `fileDialog.openFile`, `fileTransfer.download` and `fileTransfer.selectUploadFile` for the `main` window. The smoke view calls those APIs; Swift host returns `capabilityResult` with `permissionReason=manifest-allow` and manifest metadata, with clipboard backed by native `NSPasteboard`, file dialog backed by AppKit `NSOpenPanel`, bounded download writing to a controlled test path and upload/select-file reading metadata plus sampled bytes from a controlled test file. The same click also sends `diagnostics.deniedCapability`, which is intentionally absent from the manifest and must return `permissionDecision=denied` with `permissionReason=manifest-denied`.
- The file-transfer smoke is deliberately narrow: traces redact the body and record byte count, filename, path, operation and permission metadata. It does not claim full Vaadin Upload/Download parity.
- This is not the full Vaadin Flow transport yet; the hidden local UIDL applier remains as a diagnostic fallback. The current push/recovery path is a controlled ordering smoke, and the current resource execution path is a Flow client classification/lazy-lookup plus BigDecimalField, Checkbox, one theme/static classpath resource, one generated-flow-imports fixture resource, one real dev-bundle generated-flow-imports chunk execution path, one v1.9 loadOnDemand diagnostic bridge/blocker, one v1.10 Flow lazy dependency execution path, one v1.11 generated loadOnDemand chunk mapping/staging blocker, one v1.12 generated-flow-imports no-op table / chunk-file-not-generated proof, one production-bundle stats graph resource, one production runtime staged execution attempt, one v1.13 production owner contract/staging boundary, one v1.14 production owner import attempt / relative dependency blocker boundary, one v1.15 production owner dependency resolver / missing-real-artifact boundary, one v1.16 production owner ordering / component reuse boundary, one v1.17 host-owned custom-scheme/file-backed lazy dependency execution boundary, one v1.18 production owner custom-scheme root/dependency graph boundary, one v1.19 production owner side-effect / reuse decision boundary, one v1.20 owner-owned runtime reuse attempt boundary and one dev-mode package-lock graph resource smoke, not durable reconnect, full Flow Push/WebSocket parity, production owner import/side-effect success or dev-mode replacement.
